## Waitlist implementation

Email is required, with browser and server validation. No name, account, credentials or financial data is collected. A required, unchecked consent checkbox explicitly covers launch and early-access emails. The privacy notice is linked at collection. The server records normalised email, signup time, consent version (`waitlist-2026-11-16`), consent time and a sanitised campaign-source label. It records no raw IP in the lead table.

SQLite uses a unique email primary key, parameterised statements, WAL journalling and `synchronous=FULL`. A successful response is sent only after insertion commits. Duplicates get the same success response, preserving their original consent record and avoiding email enumeration. A write failure gets 503. The form reports validation, pending, success, connectivity and server errors accessibly. Retries after timeouts are safe.

Abuse prevention includes a honeypot, 2 KiB request limit, exact-origin checks, JSON-only submission, request timeouts and a durable rate limit of eight attempts per network address per 15-minute window. Addresses are HMAC-hashed with the server secret; expired records are removed on subsequent requests. Invalid attempts count towards the limit. Distributed botnets remain a limitation; monitor aggregate load and add provider-level controls if needed. The database is private, mode 0600; its directory is created 0700 when new. Avoid exposing the database directory through another web server.

No external mailing provider or automatic email send is configured. No double opt-in is claimed. Use a reviewed consent-compatible communication process before sending updates.

### Authorised access/export and deletion

Use a restricted hosting console/SSH session and environment secret access, never a browser route:

```sh
umask 077
WAITLIST_DB=/var/lib/prospect/waitlist.sqlite npm run --silent export:waitlist > /private/path/waitlist.csv
```

CSV fields are quoted, double quotes escaped and spreadsheet-formula prefixes neutralised. The file contains personal data; limit access and remove exports when no longer needed. Do not attach real exports to issues, CI logs or PRs. For access, withdrawal or erasure requests, use an authorised database console and parameterised queries, and apply the same retention rules to exports/backups. Keep backups encrypted with restricted access and test restore procedures. Use SQLite's online backup facility rather than copying an active database without its WAL.

## Production configuration and deployment

**Live waitlist requirement remains blocked, not passed.** Local persistence and restart behaviour are verified. No production database, persistent volume, deployment credentials/configuration or production smoke signup was supplied or created.

Required variables:

| Variable | Purpose |
| --- | --- |
| `WAITLIST_DB` | Absolute file on a private persistent mounted volume; e.g. `/var/lib/prospect/waitlist.sqlite` |
| `WAITLIST_RATE_SECRET` | Random secret of at least 32 characters, managed only in server-side hosting secrets |
| `PUBLIC_ORIGIN` | Exact externally visible origin, default `https://prospectpartnership.co.uk`; must match browser Origin for form requests |
| `HOST` | Default loopback; container sets `0.0.0.0` |
| `PORT` | Runtime listener, default 3000 |
| `TRUST_PROXY` | Default `0`; set `1` only behind an exclusive trusted proxy that overwrites X-Forwarded-For with the actual client address |

Release steps for an authorised operator after review:

1. Review/merge the PR only when authorised; no automatic production deployment is included in CI. If the existing host auto-deploys main, pause/reconfigure that integration before merging: static-only hosting cannot supply the API.
2. Use the supplied Dockerfile or Node 24 host. Run `npm ci --ignore-scripts`, `npm run build`, and `npm start` (runtime does not require npm packages). CI verifies generated pages match source.
3. Mount a private persistent volume at the database directory, writable by the unprivileged runtime user. Confirm permissions, encryption, backups and retention procedures. Use **one replica** with this local SQLite implementation. Multi-instance/ephemeral/serverless deployment needs a shared durable datastore and shared rate limits instead.
4. Set the variables above via the host secret manager. Generate the rate secret securely; never place it in frontend code, Docker build args or Git. Configure HTTPS and a trusted reverse proxy, aggregate abuse controls and uptime/error monitoring without lead payloads.
5. In a staging environment, verify one controlled signup, database row, consent record, duplicate result, rate limit, export and persistence across an actual service restart. Check the privacy notice against the selected hosting/data-processing providers and transfer arrangements.
6. Verify DNS/custom-domain routing and same-origin `/api/waitlist`. Do not publish only the static root as a finished launch. Missing credentials intentionally produce a clear 503, but this is not a working live waitlist.
7. Run Firefox/WebKit, assistive-technology and production-host Lighthouse checks. Review legal/provider details, the missing official LinkedIn destination and email communication/withdrawal workflow. Add real-user performance monitoring only with an appropriate privacy basis.
8. Deploy only on explicit authorisation. Preserve any existing production records; this implementation creates tables if absent and contains no destructive migration. Roll back code independently from the persistent volume; never delete the volume to roll back a frontend change.
